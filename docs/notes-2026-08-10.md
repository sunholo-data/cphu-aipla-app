## ku.dk domains — blocked on DNSSEC, needs CPH IT action

Checked 2026-08-10 after CPH IT said the domains should be mapped.

**Verdict: needs intervention. Will not self-solve before the pilot.**

CPH IT created all four records correctly — right addresses, right structure:

| Name | A | AAAA | Env |
|---|---|---|---|
| `aipla.ku.dk` | 8.233.216.35 | 2600:1901:0:faa7:: | prod |
| `aipla-sandbox.ku.dk` | 8.233.216.35 | 2600:1901:0:faa7:: | prod |
| `aipla-test.ku.dk` | 136.68.144.79 | 2600:1901:0:e627:: | test |
| `aipla-test-sandbox.ku.dk` | 136.68.144.79 | 2600:1901:0:e627:: | test |

They are only reliably visible with DNSSEC validation disabled. Behaviour is
resolver-dependent, which is the crux of the whole dispute: **Google** refuses
them (SERVFAIL, or authenticated NXDOMAIN once it has the parent's denial
cached), while **Cloudflare and UCPH's own resolver return the record** as
insecure. Lenient validators accept a signed "does not exist" alongside a real
answer; strict ones call it forged. This is why CPH IT could not reproduce it.

It only has to matter to one resolver, and it does: **Google is strict, and
Google is the CA for our certificates.**

**Root cause.** `ku.dk` is signed in bulk, not incrementally — every RRSIG in
the zone shares the window `2026-07-30 → 2026-08-20`, including the DNSKEY's
own signature. The SOA serial is `2026081005`, so content changes daily while
signatures stay frozen at 30 July. The names were added today (child-zone
serials `2026081003/04`), so the signed NSEC chain still carries the gap

```
www.ailaw.ku.dk.  NSEC  www.airpolife.ku.dk.
```

and all four `aipla*` names sort inside it (`ailaw` < `aipla` <
`aipla-sandbox` < `aipla-test` < `aipla-test-sandbox` < `airpolife`). The zone
therefore serves a signed proof the names do not exist alongside unsigned
records saying they do — bogus, so validating resolvers refuse to answer.

**The setup itself is fine.** `ind`, `science`, `sund`, `math`, `di`, `nbi`
are delegated identically (own SOA, `NS ns1/ns2.ku.dk`, no DS) and resolve
correctly as insecure delegations (`Status=0, AD=False`). No redesign needed.

**Our side is complete.** Bypassing DNS with `--resolve`, the ALB answers on
all four hostnames and the Host-header split (frontend vs sandbox) is correct
— 301 to HTTPS on each. The four Google-managed certs were created 2026-08-03
and have sat `PROVISIONING / FAILED_NOT_VISIBLE` for seven days; they issue
automatically ~15-60 min after the names validate. If any don't, recreating
them is a one-line Terraform op.

**Why not wait.** Best case it self-heals at the next bulk signing, due near
the 2026-08-20 expiry — after the pilot starts on the 14th. And that is an
inference about their schedule, not a commitment.

Reproduce:

```bash
dig +short aipla.ku.dk A          # SERVFAIL, empty
dig +cd +short aipla.ku.dk A      # 8.233.216.35 (validation disabled)
curl -s "https://dns.google/resolve?name=aipla.ku.dk&type=A"   # Status 2
gcloud compute ssl-certificates list --project=aipla-prod-2026 \
  --format='table(name,managed.status,managed.domainStatus)'
```

### Update 2026-08-11 — CPH IT closed the tickets

CPH IT closed both tickets: they could not reproduce it, and their own
Zonemaster run ("DS in delegation requires signed zone") turned out to be a
typo on their side — a DS pasted into an undelegated test, which is why no DS
exists in the live zone. That error was never part of our evidence.

State re-verified 2026-08-11 09:07 UTC: unchanged. Records correct, `ku.dk`
signatures still dated 2026-07-30, all four names NXDOMAIN on the parent-side
DS query, certs still `FAILED_NOT_VISIBLE`.

**The decisive test**, needing no third-party tool, against UCPH's own server:

```
dig @ns1.ku.dk +norec science.ku.dk DS   # NOERROR  — exists, no DS: fine
dig @ns1.ku.dk +norec aipla.ku.dk   DS   # NXDOMAIN — not in ku.dk's signed data
```

NXDOMAIN does not mean "no DS" — that is NOERROR, which `science.ku.dk`
returns. It means the name does not exist. Note `science.ku.dk` is itself
unsigned and works fine, so "sign the child zone" is not the fix; the
delegation just needs to be inside `ku.dk`'s current signatures.

**Expected resolution without anyone acting: ~2026-08-20.** Every RRSIG in
`ku.dk` expires then, so a re-signing run is forced — otherwise all of `ku.dk`
goes bogus. That is after the 2026-08-14 pilot start, plus up to an hour each
for negative-cache expiry and certificate issue.

**Decision:** stop working the ticket. Escalate internally (Jesper), monitor
with `make check-domains`, run the pilot on `run.app` URLs if needed. Our side
is fully verified correct — LB, host-header split, certs, Terraform, and the
sandbox already accepts the `ku.dk` origins as embedders in both envs.
