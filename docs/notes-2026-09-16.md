## Simulations — teacher authoring workflow

**The sim authoring prompt was demoed live in the meeting, in ChatGPT (not
our app).** It fetched well and worked as a first pass, but the resulting sim
app itself wasn't good quality yet. Read as validating the *workflow* — the
prompt is genuinely usable as the first step of a teacher setting up a
simulation for a class/activity, and something a teacher could iterate on —
rather than a finished-artefact result. This is exactly the shape
[1.1.104 simulation-import-pipeline](design/aipla/v1.1.0-feedback/simulation-import-pipeline.md)
(**D6**, 9 Sept) already assumes: a teacher-drafted artefact arrives as a
file and goes through a **reviewed pipeline** (ADR-013 gates + human
approval), not straight into the classroom — so a rough first pass from
ChatGPT is the expected starting point, not a problem with the approach.

**Idea raised: our prompt could go further than ChatGPT's default and help
ensure the physics itself is correct** — e.g. by asking the authoring prompt
to cite its references/sources for the physics content it generates, so
accuracy can be checked rather than trusted. Not decided or scoped — a
possible next iteration of `frontend/public/sim-authoring-prompt.txt`
(shared above), worth weighing against
[1.1.115 verify_sim](design/aipla/v2.1.0-extension/sim-verify-mcp.md) (a
chat-side MCP tool to check a draft sim) as the two candidate places to add a
correctness check — prompt-time vs. verify-time.

**Strategic question raised: on-the-fly sim generation inside chat, and how to
guarantee accuracy.** The ambition — a sim generated live in a chat, not
authored ahead of time — is real, but it's a much sharper version of the trust
problem than the teacher-authoring workflow above: no human review sits
between generation and the student, and the concern stated in the meeting was
explicit — **even 95% physics-correct is not good enough, because the 5% that
misleads a student risks destroying trust in the whole product, not just that
one sim.**

⚠️ **This isn't a new question — there's already a design doc that reached a
specific answer**:
[post-pilot/student-generated-apps-tldraw.md §6–9](design/aipla/post-pilot/student-generated-apps-tldraw.md).
Its finding, in short: **free-form "AI writes the physics code" scores
Axiom 2 (Earned Trust) at -1** — wrong physics is possible and would mislead a
student, exactly the risk raised today. The doc's answer is **not** "review
harder" or "verify after the fact" — it's **don't let the model write physics
code at all**: build one small trusted **matter.js physics engine** as a
vetted artefact, and have the model only ever fill in a **validated JSON
scene** (initial conditions, objects, parameters) that the fixed, human-vetted
engine then computes. That turns "wrong physics" into "an implausible-but-legal
setup" — a scale/plausibility residual the tutor can even flag, not a
law-of-physics error. Same idea flips **Axiom 9 (Secure by Construction)**
too: a scene is data, never executable code, so there's nothing to sandbox
against because nothing untrusted executes. Recommendation in that doc: build
the engine + scene schema now (cheap, safe, independently valuable); treat
free-form AI-generated code as parked/not-recommended. **Worth bringing this
doc into the discussion rather than re-deriving the answer from scratch.**

**The concept map raised as the anchor for both accuracy and scope — this is
already decided, just not built.** The idea that the concept/knowledge map
could steer the tutor and stop it drifting off-topic or too advanced matches
[1.1.90 bounded-tutoring-answer-trees](design/aipla/v1.1.0-feedback/bounded-tutoring-answer-trees.md)
almost exactly — **P1, the most-repeated theme of the 1 September meeting**,
with a decision already taken (**D2, 2026-09-02**): answer trees are
teacher-authored, the AI navigates them, and the concept map is what bounds
what the tutor is allowed to talk about. It builds directly on
[1.1.65 living-concept-map](design/aipla/v1.1.0-feedback/living-concept-map.md),
which is **already shipped to dev** (the map element, graph view, per-group
checkpoint tracking) — so the map itself exists; what's missing is using it to
bound the tutor's conversation. Estimated ~5–7d phased, explicitly paired with
[1.1.98 teaching-prompt-standardisation](design/aipla/v1.1.0-feedback/teaching-prompt-standardisation.md)
("build them together" — same offload problem from two directions). **Status:
still fully OPEN design, no implementation commits exist.** Given the "tutor
too advanced / off-topic" feedback recurring again today, this looks like a
strong candidate to actually schedule rather than continuing to defer it.

**Follow-up idea: resurrect automatic concept-graph generation, and get most
classes a map.** Two things worth separating when this gets scoped: (a) the
co-pilot **already has an on-demand `propose_concept_map` tool**
(`backend/adk/authoring_tools.py`, wired into the activity builder's
`_AuthoringCopilot`) that drafts a map for a teacher to accept/edit — so
per-activity generation exists today, gated on a teacher asking for it; (b)
"resurrecting **automatic**" and "most classes have one" both point at
something more proactive than that — either generating a draft map
unprompted (e.g. at activity-authoring time, or from the curriculum corpus —
`living-concept-map.md` already lists curriculum-library "propose-from-corpus"
as an input) or **batch-drafting maps across existing classes** rather than
one at a time. Not clear from today's discussion which of these is meant, or
whether "automatic" refers to a specific earlier capability — no prior
"automatic" generation is documented in `concept-map-sprint.md` or
`living-concept-map.md`, so this may be describing a new ask rather than
reviving something that existed. **Needs scoping**, and it feeds directly into
1.1.90 above — a class with no map has nothing for the answer tree to bound
against.

**Extended ask: a class-level concept graph spanning the year, filled in as
groups complete classes/activities over time — plus linking activities to
each other (starting with activities, not the full class).** This **likely
resolves the earlier "activity linking" question** from item 3 above — read
together, it sounds like the same thing: a graph that ties activities to one
another via shared/prerequisite concepts, which is also how a class-level
longitudinal view would be built up. Flagged as *likely*, not certain — worth
a one-line confirmation next meeting.

⚠️ **This is well-trodden ground with a specific, useful existing answer —
worth walking through directly:**
[longitudinal-concept-evidence.md §"The decision that cannot wait"](design/aipla/v1.1.0-feedback/longitudinal-concept-evidence.md)

**Option 1 — class-level longitudinal only — is precisely what's being asked

require a decision that doc says "cannot be decided retroactively," and the

anything beyond class/group level may already be foreclosed for this year's

students) is the one still fully open.

**What already exists vs. what doesn't, for this specific ask:**
